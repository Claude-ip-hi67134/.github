<p>把环境交接给同事，最容易出问题的地方不是技术，是「说不上来」。问他这个号用的什么时区、UA 主版本多少、出口是哪条线，答案往往是「我一直就这么用的」。参数说明书的用处就在这里：把口头经验写成有默认值、有取值范围、有调整边界的规格表，换人照表配一遍，环境就一致了。下面按网络层、浏览器层、账号层三段列参数，最后给后台留档的字段定义。</p>
<h2>一、参数总表：先有规格再谈配置</h2>
<p>规格表不是配置文件的复制，而是配置文件背后那些「为什么这么设」的决定。每行至少写清四件事：参数名、作用、默认值、可调整范围。四件事缺一件，接手的人就只能猜。</p>

<h3>规格表怎么维护</h3>
<p>放仓库里，和配置文件同目录，改配置必须同步改表。评审时只看表，不看配置文件，因为表是人能读的。每季度核对一次，把已经不再使用的参数删掉，别让表越长越没人看。</p>
<h2>二、网络层参数：出口、协议、超时</h2>
<p>网络层参数决定连通性和稳定性，调错的表现是「时通时不通」，最难排查。三个参数最要紧：出口、协议、超时。</p>
<h3>出口绑定与协议选择</h3>
<p>静态住宅的核心价值是出口不变，所以绑定关系必须是显式的：号到线一对一，写在调度表里。协议上 HTTP 代理兼容性最好，SOCKS5 支持 UDP 且对某些客户端更友好；同一池内统一一种，混用会让排查时多一个变量。</p>
<h3>超时与重试</h3>
<p>连接超时建议 8 到 15 秒，读超时 30 到 60 秒，重试两次为上限。重试次数设太高会放大故障：一条坏线被重试三次，体感就是卡了三倍时长。把重试和熔断配合起来，连续失败三次就把这条线踢出可用列表，十分钟后再探活。</p>

<h2>三、浏览器层参数：时区、语言、指纹项</h2>
<p>浏览器层最容易「看起来差不多但实际不一致」。同一个号今天用 1440×900，明天用 1920×1080，页面渲染差异会体现在截图、字体加载、甚至某些布局判断上。所有项都按表固定，别随手改。</p>
<h3>时区与语言要跟着出口走</h3>
<p>规则只有一条：时区与出口城市一致，语言与地区主语言一致。出口在洛杉矶就用 America/Los_Angeles，语言头给 en-US 加一个 en。很多人图省事把时区固定成本地时区，短期看不出问题，长期就是明显的不一致。</p>
<h3>指纹项里哪些必须固定</h3>
<p>UA、分辨率、设备像素比、字体列表、Canvas 与 WebGL 的默认值，这五项必须固定并在表里登记。其余项可以随内核升级自然变化，不必强行锁死。锁得越死，升级时越容易出兼容问题，反而增加维护量。</p>
<h2>四、账号层参数与后台留档字段</h2>
<p>后台操作留档的意义是「谁在什么时候改了什么，改之前是什么」。字段设计围绕这一句展开，不追求多，追求能还原。</p>
<h3>留档的六个字段</h3>
<p>操作时间、操作人、对象（号或线路）、动作（新增、变更、停用）、变更前后值、关联工单号。六个字段缺一不可，尤其「变更前后值」，没有它就无法回滚。</p>

<h3>批量开号怎么省掉重复配置</h3>
<p>把参数表做成模板文件，开号时只填三个变量：号 ID、地区、绑定的线路。其余全部继承模板，不允许单个号单独改时区或分辨率，需要例外就走变更流程并在留档里写明原因。这样批量开的号天然一致，也不会因为某个人的习惯造成偏差。</p>
<h2>常见问答</h2>
<h3>参数表要不要写进配置文件注释？</h3>
<p>答：可以，但不要只写在注释里。注释随文件走，人走了文件可能也跟着丢；规格表放独立文档并纳入版本管理，才具备交接价值。两处都写最好，冲突时以文档为准。</p>
<h3>静态 IP 真的不会变吗？</h3>
<p>答：在合同期内通常不变，但服务商上游调整、线路迁移都可能造成变化。做法是每周探测一次出口并记录，出现变化能第一时间发现，而不是等到业务异常才反查。</p>
<h3>团队规模小，留档会不会太麻烦？</h3>
<p>答：小团队更该留，因为每个人负责的号多，记忆负担重。简化方式是只对变更类操作留档，日常巡检只记异常，这样一天也就几条记录，成本很低。</p>
<h3>指纹项要全部固定吗？</h3>
<p>答：不必。固定核心五项即可，其余随内核自然变化更真实。全部锁死会让环境显得僵化，也会在浏览器升级时带来大量兼容问题，维护成本高于收益。</p>
